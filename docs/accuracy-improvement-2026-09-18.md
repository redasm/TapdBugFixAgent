# 自动修复准确率调研与改进方案

调研日期：2026-09-18。代码基线：`1c97082`。数据来源：本地 `tapd_agent_v2.db` 的 14 条人工反馈、对应调查/验证/评审记录，以及当前代码和配置。本文是设计建议，未修改执行流程或重新运行工单。

## 1. 结论与优先级

有明确的改进空间。当前最值得投入的是 **业务验收条件、人工反馈复用和行为验证**，随后是评审独立性与代码关系检索。现有项目已经具有调查、修复、验证、独立评审、范围限制和重试证据，适合在这些阶段补充证据和检查，而不必重写整套 Agent。

建议先做三件事：

1. 把本次 7 个“修改后接受或拒绝”案例整理成可复查的失败案例，并建立按尝试保存的评测基线。
2. 调查结果增加业务验收条件、关键数据含义、需要保持的行为和已有复用点；把经过核实的历史经验按相关性送入调查。
3. 机器验证区分类型检查、业务行为测试与运行时验收；优先为地图判定、招募列表时序、UI 生命周期构建少量能执行真实代码的针对性验证。

提高候选精确率和提高原样接受率是两个目标。减少拒绝主要依赖业务条件与定位正确；减少人工修改还需要符合项目的接口复用和生命周期约定。

## 2. 目前的 71.4% 表示什么

数据库与截图吻合：

| 人工结论 | 数量 | 占已评审案例 |
|---|---:|---:|
| 原样接受 | 7 | 50.0% |
| 修改后接受 | 3 | 21.4% |
| 拒绝 | 4 | 28.6% |
| 合计 | 14 | 100% |

`src/state.ts:313` 的候选精确率为 `(原样接受 + 修改后接受) / 有人工决策的 Bug 数`，因此是 `10/14 = 71.4%`。接受的 10 个案例中，3 个仍需人工修改，即人工修改率为 30%。

这是**人工接受口径**，不能直接解释为 71.4% 的补丁已经独立完成修复。剩余 13 个 pending 任务不在这个分母中，也不能从截图的“机器验证通过 0”推断历史任务没有执行过验证；该栏是当前状态数量。

样本较少：改变一个案例的结论，就会让当前比例变动约 7.1 个百分点。以二项分布假设计算，10/14 的 Wilson 95% 区间约为 45.4%–88.3%；这只是样本不确定性的参考，案例集中在地图/UI、版本与模型不同，不能视为随机抽样的生产准确率估计。

### 现有统计需要修正的解释边界

- **按 Bug 记录，未按候选版本记录。** `job_feedback` 没有 attempt ID、补丁哈希、当时的模型/提示词版本；`jobs` 保存的是可覆盖的当前记录。因此不能可靠地把某条反馈绑定到某一轮补丁。
- **反馈包含未完成产物。** `case-03` 的人工说明是“未做任何改动”，当前记录还有范围门禁失败；这些应单列为未产出/流程失败，不能和完整候选的根因错误混为一类。
- **人工接受不要求 Reviewer 通过。** 存在 `accepted_unchanged` 但当前 `review_findings.approved=false` 的记录。可能涉及人工接管、不同尝试或 Reviewer 误报；仅靠当前行无法确定。评审通过率不能代替人工接受率，也不能直接从这些行推导 Reviewer 的真实漏报率。
- **reopen 单独累积。** 当前 `qualityMetrics()` 将 reopen 放入单独集合，不从原接受分子中扣除。当前没有 reopen 记录，尚未影响此次 71.4%；未来需增加随访窗口下的持续有效修复率。
- **人工改动行数缺失。** 三条修改后接受的 `human_changed_lines` 都是 0，不能据此认为没有人工修改或计算节省工时。
- **样本跨版本、跨模型。** 反馈时间覆盖 9 月 3–18 日，代码在此期间多次调整；不应把历史错误全部认定为当前版本仍会复现，也不能据此给模型排名。

## 3. 七个非原样接受案例给出的信号

本公开副本使用匿名案例编号，标题和反馈均为脱敏概述；对应数据集保留标签统计，不提供原始工单身份。人工反馈作为项目事实线索，仍需与对应候选和最终人工补丁对齐；不是可以不加核查直接执行的指令。

| Bug | 人工反馈/记录要点 | 暴露的问题 | 对应改进 |
|---|---|---|---|
| case-05 任务追踪报错 | 反馈指出不能在数据创建方法中直接 return，应保留数据并由显隐管理器控制显隐；当前调查却主要讨论节点配置，且带范围失败 | 业务不变量与尝试归属均需核对，不能只从报错附近补判空 | 对齐候选版本；明确“数据创建”和“显示控制”的责任及触发链 |
| case-06 招募列表清理延迟 | 人工要求点击同意/拒绝后立即移除，回包后再按真实数据刷新；Agent 主要修改 Model 的去重、移除和清空 | 找到了可疑代码，但没有解决点击到回包之间的用户行为 | 验收条件明确事件顺序；测试回包前状态、成功/失败回包和刷新 |
| case-08 副本地图缺提示 | 人工要求检查目标地图是否有“地图切块配置”；补丁检查关卡 ID 与基础地图配置 | 相近配置概念被当作相同条件 | 记录每个 ID/配置的业务含义；用“基础地图配置有而切块缺失”的反例区分 |
| case-03 删除图标配置后显示异常 | 标记为定位错误，但理由是“未做任何改动”；当前记录有 CL 和文件名，缺完整验证 | 反馈标签不足以确认真实失败环节 | 保存真实非空 diff、交付状态和候选 ID；核对后再归类 |
| case-10 就近传送后地图未关闭 | 人工去掉多余的关闭调用，因为父视图关闭时会主动关闭二级 UI | 没有完整理解关闭链的责任，加入了重复操作 | 提供父视图→子视图关闭链和释放所有者；验证只执行必要关闭 |
| case-11 边缘弹窗出屏 | Agent 参考已有视口适配方法复制实现；人工要求抽成统一接口 | 识别到了同类实现，但未满足复用约定 | 计划阶段列出“已有实现/复用方案”，允许经重新审查后扩大必要文件集合 |
| case-13 跨地图传送提示 | 人工指出应比较目标与玩家所在地图 ID，而非资源路径；Reviewer 认可路径比较但拦截了缺失文本 ID | 修复与评审共享同一语义假设；文本资源也是完整交付依赖 | 验收矩阵涵盖 ID 与路径不等价；独立核对判定条件；检查文本 ID 可解析 |

两个具体观察特别值得注意：

- `case-08` 的调查自报置信度为 0.94，最后因不符合业务条件被拒；`case-12` 自报 0.30，却原样接受。现有置信度未经校准，不适合直接设置 0.8 之类的硬门槛。
- `case-11` 已经找到了同模块的现有实现，问题并非单纯“搜不到代码”。既要改善检索，也要在计划里处理复用和必要范围扩展，避免把“最少文件”误当成“最小完整修复”。

## 4. 查阅资料及适用范围

以下资料均在本次调研中读取了原文页面；Agentless 还读取了正文的定位、验证和消融实验部分。公开基准以开源代码任务为主，与本项目的游戏业务、P4、Unreal 运行时和资源依赖不同，不能直接套用其成绩。

| 资料 | 可借鉴的方法 | 如何用于本项目 |
|---|---|---|
| [Agentless: Demystifying LLM-based Software Engineering Agents](https://arxiv.org/abs/2407.01489)，2024；[正文](https://arxiv.org/html/2407.01489v2) | 分层定位到文件、符号、编辑位置；生成复现测试；结合已有回归测试筛选补丁 | 现有三阶段结构已经接近。重点补上能实际执行的复现验证，以及有预算限制的不同定位方案比较 |
| [SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering](https://arxiv.org/abs/2405.15793)，2024 | 工具与环境接口设计会影响代码导航、编辑与测试效果 | 扩展现有 scoped search：返回符号定义、引用、调用点、配置来源等明确证据，降低盲搜成本 |
| [Aider Repository map](https://aider.chat/docs/repomap.html) | 用类型、函数签名和依赖关系构造精简仓库地图，按相关性和 token 预算选取上下文 | 从地图/UI 模块试点符号与关系摘要，帮助发现可复用接口和生命周期所有者；不需要直接引入整套 Aider |
| [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，2025-09-29 | 控制上下文规模，提供高信息量示例，按需检索并维护结构化笔记 | 以少量相关历史经验、明确业务不变量代替不断追加通用提示词；失败重试优先补缺失证据 |
| [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 从人工检查和用户失败建立评测；同时测应发生/不应发生的行为；隔离试验，结合确定性、模型与人工评价 | 将当前案例变成开发回归集，新增时间留出集；对 Reviewer 用人工反馈校准；避免共享工作区和历史答案污染 |

Agentless §5.2.3 的消融实验尤其相关：300 个 SWE-bench Lite 问题上，仅多数投票得到 77 个正确修复，加入回归测试后为 81 个，再加入生成的复现测试后为 96 个。后一步提高的是该实验的 5 个百分点，支持“验证质量能改善补丁选择”，**不代表本项目能固定增加 5 个百分点**。

论文也明确承认生成测试可能不正确，因此不能只让 Agent 生成一个测试再用该测试给自己打分。测试必须核对业务预期、在旧代码上确实暴露目标问题，并通过其他正常场景检查。

当前 `review.ts` 会对特定措辞的“仅缺人工运行时验证” medium finding 降为 low，并以是否存在阻断 finding 计算通过。其避免因无法运行 UE 而拒绝所有候选的出发点可以保留，但应拆开“代码缺陷”和“验证覆盖”两个字段，避免仅靠自然语言正则推断风险，也避免把评审通过显示成行为已经验证。

当前流程已有 `revertUnchanged` 和真实 diff 接管等措施。因此，对“未做改动”历史案例先复查其发生版本，不能据单条反馈就断言当前门禁还存在同样缺陷。

## 6. 具体设计

### P0：建立可重放、可归因的基线

新增不可覆盖的 `repair_attempts` / `candidate_feedback` 记录，或等价的结构化试验快照：

- `attempt_id`、`candidate_id`、`bug_id`、输入快照/哈希。
- P4 文件 revision/changelist、Git base commit、资源和配置版本。
- 修复与评审模型、提示词哈希、工具/Agent 版本、运行预算。
- 调查、实际 diff 与哈希、机器命令/退出码/日志引用、评审原始结果、人工最终决策。
- 人工最终补丁或提交引用、修改类别、修改耗时（可选）、reopen 关联候选及时间。
- 阶段结果：未产出、部分候选、完整候选、机器失败、人工接管，避免只靠文件名推定成功。

保留原始标签；例如“定位错误 + 未做改动”增加复核标记，不静默改成推测的类别。将人工改动量中的“未知”与 0 分开。

至少同时报告：

1. **候选精确率**：已人工验收的完整候选中，原样或修改后接受的比例。
2. **原样接受率**：相同分母中，原样接受的比例。
3. **端到端有效率**：固定输入批次全部任务中，完成规定验收的比例；未产出和弃权仍计入分母，避免通过少接任务抬高成绩。
4. **候选覆盖率与反馈覆盖率**：产生完整候选/全部输入，以及已验收/完整候选。
5. **人工修改成本与持续有效率**：人工修改时间、修改类别，以及统一随访窗口内的 reopen。
6. **效率**：每例模型成本、运行时长、工具失败率；成本与时长必须来自记录。

旧统计仍保留并标注“历史人工接受口径”，新口径另设起点，不能把换分母造成的上升当成修复能力提升。

涉及数据库结构调整时，保留现有反馈和原始库，采用版本化新增表/导入，不沿用开发期“删库重建”的简化做法。

### P1：业务验收条件与经验检索

扩展 `InvestigationResult`，由调查阶段整理：

```ts
interface RepairContract {
  acceptance_cases: Array<{
    given: string;
    when: string;
    then: string;
    source_refs: string[];
  }>;
  preserved_behaviors: string[];
  domain_facts: Array<{
    concept: string;
    meaning: string;
    source_refs: string[];
  }>;
  reuse_options: Array<{
    symbol: string;
    action: "reuse" | "extract" | "not_applicable";
    reason: string;
  }>;
  open_questions: string[];
}
```

这是建议的数据形状，不是本次已实现接口。`source_refs` 应关联实际读取的文件、配置、工单内容或工具输出；宿主检查来源存在，评审检查推理是否成立。

对跨地图案例，应先明确：玩家所在地图 ID、标记所属地图 ID、UI 当前浏览地图 ID、关卡 ID 与资源路径分别表示什么。验收至少包括：

- 目标与玩家在同一地图：保持正常传送。
- 目标与玩家处于不同地图：显示指定提示，并且不发起传送。
- 若项目数据允许不同地图 ID 共享资源路径，该情况仍应按地图 ID 判定；若实际不存在，作为用于区分语义的构造测试，不能伪称生产复现。
- 玩家浏览了别的地图：判断仍以玩家实际所在地图为准。
- 提示文本 ID 不存在或解析为空：记录资源依赖未完成。

新增 `src/feedbackMemory.ts`（建议），处理“人工反馈 → 待核查经验 → 可检索经验”：

- 初版只需要 SQLite/JSON 加关键词与符号匹配，数据少时不必引入向量数据库。
- 按模块、符号、错误模式和适用版本检索，先取 3–5 条，设置上下文预算。
- 每条经验包含适用条件、错误做法、经代码核实的正确原则、例外与来源。
- 调查读取经验后，必须核对当前代码；只把它当线索，不把历史文本当新指令。
- 对同一个 Bug 的人工重试可以传入已知反馈；在评测未见任务时，必须排除该 Bug 的答案及其同源变体。

首批经验可围绕“创建数据与控制显隐分离”“地图 ID 与路径不等价”“父视图关闭负责子视图清理”“同类弹窗布局复用”“申请列表回包前后的时序”整理。

计划范围保持严格，但增加受控的 `scope_amendment`：若确需提取已有共用方法，由调查补充必要文件与理由，再重新检查范围后实施。不要直接取消白名单，也不要迫使 Agent 为了单文件限制复制逻辑。

### P2：分层行为验证

验证记录区分以下证据，独立保存，不能相互替代：

| 层次 | 证据 | 可以得出的结论 |
|---|---|---|
| L0 静态检查 | 类型检查、编译、lint | 满足对应静态约束 |
| L1 业务测试 | 执行真实业务方法的单元/组件测试，包含反例 | 已验证被覆盖的业务行为 |
| L2 集成/运行时测试 | UE 自动化、PIE、实际 UI/资源状态、可重复场景脚本 | 已验证指定环境与场景 |
| L3 人工验收 | 人工游戏内复现、结果和版本记录 | 已通过约定的人工验收 |

初期优先 L1，不等待所有 UE 场景都能自动运行。纯判定逻辑和列表状态可用轻量测试依赖；涉及 UE/LGUI 时可模拟外部接口，但测试应调用实际修改的方法，不能抄一份补丁逻辑写到测试里自证。

每个行为测试保存：测试来源、修复前/后源码版本、同一测试的命令与退出码、具体断言、正常对照。先确认旧代码因目标行为失败，再确认补丁通过；环境加载失败不能记为成功复现。防止候选通过改测试期望、放宽断言或不执行实际代码获得通过。

优先覆盖：

- 地图：切块配置缺失、有 WorldMap 但缺切块、跨地图 ID、文本资源解析。
- 招募：点击后立即消失、回包后仍存在则恢复、成功移除、重复点击、失序回包。
- UI 生命周期：父视图关闭触发子视图清理一次、取消/超时路径恢复状态。
- 布局：四边/四角、不同缩放和分辨率、异步列表布局后最终位置。

当前调查阶段严格只读，不宜偷偷让它写测试。可在调查给出验收条件后，由独立的验证准备步骤在隔离测试目录生成并固定测试，再交给修复阶段；只有需要随补丁提交的测试才纳入 `planned_files`。历史重放必须在隔离的 P4 client/Git worktree 与资源环境中运行，不在现有工作区恢复旧 revision。

暂时无法自动验证的候选仍可交给人工，明确标注 L0 和待验收场景。不要因为无 UE 运行环境把所有任务阻塞，也不要给它们“行为验证通过”的标签。

### P2：让 Reviewer 独立核查业务条件

当前已使用不同模型，下一步重点改变评审输入与顺序：

1. 先给原始需求、验收条件、必要代码和 diff，让 Reviewer 判断改动是否满足用户行为。
2. 再提供调查推断，检查它是否与前一步结论一致。
3. 要求提出能够区分“看起来合理”和“真正符合要求”的反例，并关联到现有测试/具体数据流。

这是待 A/B 验证的设计假设，不能保证仅调整顺序就提高准确率。

评审输出增加 `requirement_match`、`behavioral_evidence`、`reuse_and_lifecycle`、`unverified_items`。代码缺陷、业务条件错误与缺少运行环境分别表达；保留明确缺陷阻断，不用正则把语义风险当成普通人工验收提示。

校准时同时纳入人工接受和拒绝的候选，统计漏放与误拦，避免只把 Reviewer 变得更严格。只有反馈和候选版本对齐后，才能计算这些比例。

### P3：按需代码关系检索与有限多方案

在现有搜索扩展上增加 `lookup_symbol`、`find_references`、`find_related_implementations` 等只读能力（建议名称），先覆盖 TS 模块。优先使用 TypeScript 编译器/语言服务建立符号和引用关系，再逐步补充项目自己的事件、配置和生命周期关系；不要宣称静态工具能完整恢复反射、蓝图和动态派发。

索引按 revision/文件内容增量失效，返回少量相关片段、路径、版本与截断标记。先对地图/UI 试点，衡量是否减少重复搜索、增加复用点命中，再考虑扩展到引擎。

仅当两个合理根因确实无法区分且已有验证手段时，试验两个不同定位/补丁方案。可先顺序运行；如将来并行，必须有不同 P4 client/worktree 和独立资源环境，不允许多个写 Agent 共用 default changelist 或 UE 编辑器。

最终按验收条件、行为测试、回归与范围选出一个补丁。`pass@2` 只表示两个候选中存在正确答案，最终上线指标仍是实际选出的 top-1 结果；多个模型投票不能代替验证。

## 7. 如何证明改进有效

### 数据集

- 当前 14 个案例作为开发回归集，其中 7 个非原样接受案例用于找问题，7 个原样接受案例防回归。其答案已在设计中使用，不能再当作未见测试集。
- 对历史案例补全原始代码/配置版本、最终人工补丁与验收条件；缺少这些的标为“仅可做标签分析”，不伪造完整重放能力。
- 后续新工单按时间作为留出集；同类重复工单和同一缺陷的多个变体成组划分，避免答案泄漏。先积累 30–50 个案例作工程筛查，并根据差异和方差继续积累；这个数量不保证统计显著。
- 验收同时覆盖成功行为与不应发生的行为，避免只测提示是否出现而遗漏错误传送仍被发起。

### 对照实验

| 实验 | 相对当前基线只增加的内容 | 主要关注 |
|---|---|---|
| A | 固定当前代码、模型、预算与数据版本 | 建立可复现基线 |
| B | 业务验收条件 | 根因/业务条件错误是否减少 |
| C | 在 B 上加入经核实的相关经验 | 类似错误是否减少、原样接受率是否提高 |
| D | 在 C 上加入 L1 行为验证 | 漏放错误与回归、候选覆盖率 |
| E | 在 D 上加入评审输入调整 | Reviewer 漏放与误拦 |
| F | 仅对仍失败类别试验索引/第二方案 | 增益与成本是否相称 |

同一组对照用相同初始版本和预算；试验目录、缓存和历史输出隔离。关键案例在预算允许时做多次独立运行，报告每次结果，不能只挑最好一次。人工评审尽量隐藏实验组，保留“无法判定”而不强行接受/拒绝。

评价优先看原样接受率、完整候选精确率和端到端有效率，再看成本与时间。`evaluation.ts` 的混合加权 score 可作辅助，不能让较高编译通过率抵消业务修复失败。

建议将“原样接受率达到 65%–70%、候选精确率达到 80% 以上，且覆盖率不下降、严重回归不增加”设为后续工程目标，**不是现有证据支持的收益预测**。是否达到目标以留出集和持续人工验收为准，同时报告样本数与不确定性。

## 8. 实施顺序和投入

以下是粗略开发量，取决于能否取得历史版本、最终人工补丁和目标项目测试环境，不是交付承诺。

| 阶段 | 建议工作 | 粗略投入 | 完成判断 |
|---|---|---|---|
| 第一阶段 | 尝试快照、反馈绑定、复核 7 例、按口径展示指标 | 2–3 人日 | 每条反馈可追溯到实际候选；未完成产物可单独统计 |
| 第二阶段 | RepairContract、首批领域经验、受控范围补充 | 2–4 人日 | 能解释七例中的业务条件/复用问题；原样接受案例无新增明显回归 |
| 第三阶段 | 三类高频逻辑的 L1 验证、Reviewer 校准 | 3–5 人日，取决于 UE/TS 依赖拆分 | 固定测试能在对应旧代码失败、修复后通过，并覆盖正常对照 |
| 第四阶段 | 符号关系索引、按需第二方案、更多 UE 场景 | 按前三阶段结果另估 | 在相同成本约束或可接受增量成本下，留出结果改善 |

优先完成前两阶段形成闭环，再决定行为测试基础设施的规模。现有 14 例不足以支持先微调模型；当前已配置异模型评审，也不应把再换一个模型当成主要方案。新模型可以作为后续固定基线上的独立实验。
