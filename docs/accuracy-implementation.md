# 准确率改进实施记录

2026-09-18。依据 [调研方案](accuracy-improvement-2026-09-18.md) 实施。调研文档保留当时结论，本页说明实际交付和边界。

## 已接入执行流程

| 环节 | 新行为 |
|---|---|
| 尝试审计 | 每次处理新建 attempt，保留输入、模型、执行预算、代码哈希、实际调用提示词哈希、P4 同步记录、Git base commit、修改前源码哈希、验证与评审输出；重试不覆盖以前候选 |
| 完整候选 | 必须有真实非空 diff；P4 新增/删除文件补采实际内容，二进制单列差异；失败候选单独记录 partial |
| 人工反馈 | 必须选择 candidate，仅写候选反馈表；反馈、人工修改量、耗时、类别、最终补丁引用与 reopen 关联该版本；旧候选反馈不覆盖新尝试状态 |
| 数据保存 | 当前 schema 新建审计表；不自动迁移旧 schema。历史标签保持原样且只读，不能可靠关联的旧补丁不猜测迁入新指标 |
| 业务验收 | 调查必须输出 given/when/then、正常对照、业务概念、复用点；引用必须指向已有观察或非空工单字段，影响修复方向的未确认问题不能进入实施 |
| 相关反馈 | 最多4条/5000字符，按符号、中文词组与当前任务相关性检索；人工经验标为待当前代码核查，不能当命令执行 |
| 范围补充 | 调查可请求 scope_amendment；修改前最多一轮只读复核，仅可添加申请的具体文件，保留原验收条件并重新经过路径、存在性、文件数量限制 |
| 行为验证 | 每次修复前从目录自动发现脚本及其 files 声明，按计划文件匹配并冻结；在实际源码上执行前后同一断言，保存测试哈希和前后源码哈希。环境错误不算复现，断言回归阻止交付 |
| 独立评审 | 原始需求/验收条件/diff 在调查假设之前；新评审必须返回业务、行为证据、复用生命周期、未验证项。明确缺陷不再因“人工验证”措辞自动降级 |
| 代码导航 | lookup_symbol、find_references、find_related_implementations 提供 TS AST 声明与标识符候选；有行号、片段、内容哈希、截断提示，缓存随内容变化失效 |
| 成本 | 记录 Pi 提供的数值成本、工具调用/失败和实际耗时；缺少价格或调用结束记录时成本为 null，不编造0元 |

源文件引用校验能证明引用存在，不能证明业务推断正确。Reviewer 仍需核对语义。符号工具的 references 是同名标识符候选，不是完整类型解析；动态派发、蓝图、反射需要进一步查看代码/运行时。

## 使用方法

执行 `npm run build` 后按正常流程重启服务，新的审计、验收条件和评审协议自动生效。本次没有重启生产服务、启动工单修复队列或回写 TAPD。

行为验证按仓库配置测试目录，不再逐项配置脚本与源码路径。旧列表格式直接拒绝，使用以下唯一格式：

```yaml
behavior_checks:
  enabled: true
  directory: behavior-suites
  disabled: []
  timeout_sec: 30
```

本地配置中的测试目录和引擎构建入口由用户指定；实际路径及凭据仅保存在不提交的本地配置中。

- directory 相对 config 文件；递归发现 `.mjs`，测试名为目录内相对路径去掉扩展名。添加、修改、删除脚本从下次修复生效，无需重启；配置修改需重启。
- 脚本直接导出 `export const files = ['相对源码路径']`，路径相对 repo.path，精确匹配计划文件；测试体复用该数组，路径只维护一处。发现阶段只静态解析声明，不执行模块。
- disabled 按测试名停用，例如 `[map-tiles]`；enabled=false 停用整个目录。完整增删说明和脚本模板见 [维护指南](../behavior-suites/README.md)。
- 脚本受信任程度与 verify_cmds 相同，应放在 Agent 修改范围之外；前后执行使用内存中冻结的原始脚本。
- suite 导出 `default async ({test,assert,loadMembers}) => ...`；test 的 kind 为 reproduction 或 regression。
- loadMembers 从目标项目当前 TS AST 取真实成员执行，依赖通过显式替身传入。它不重建整个 UE 运行时、父类构造或引擎反射环境。
- 单套默认30秒，允许1–300秒，支持取消。脚本不超过100KB。脚本中的本地相对 import 不受支持。

三套已提供的 project 专项：地图切块配置4个断言，招募同意/拒绝和个人/队伍回包边界5个断言，标记销毁状态恢复2个断言。当前游戏源码只读执行11个断言全部通过。它们验证的是成员边界，不覆盖网络乱序、文本资源解析、UE 真实销毁链、布局缩放等全部场景。

只有至少一个目标行为“旧代码失败→新代码通过”，全部测试通过，且存在“前后均通过”的正常对照，才报告 L1。旧代码本来通过的专项可作回归检查，不会冒充本次 Bug 已复现。无匹配测试或环境不可用时保留 L0 和待验收项。L2/L3 不自动生成，仍由真实运行时与人工验收提供。

## 统计与评测

管理台将只读“历史人工接受口径”与新候选指标分开；API 返回 `quality.historical` 和 `quality.candidates`。新反馈不会改变历史基线，只计入完整候选精确率、原样接受率、候选覆盖率、反馈覆盖率和端到端有效率。`GET /api/quality/candidates?cohort=production-v1&followup_days=14` 返回持续有效率、耗时、已知人工成本等细项。输入从同步登记或首次处理开始记录，同一 cohort/workspace/bug 的重试不增加输入分母；未产出仍计入分母。生产 cohort 是持续累积口径，严格固定批次对照应使用下面的冻结数据集。

[14个历史开发案例](accuracy-development-cases.json) 为脱敏公开副本：案例编号、描述及其哈希均已匿名化，时间仅保留到日。保存7个原样接受、3个修改后接受、4个拒绝。保留原始标签与行数；人工修改行数的历史0同时保留原值并标明未知。case-03 标记标签与“未改动”理由需复核。全部为 label_only：目前缺少精确初始源码/资源版本和最终人工补丁，不能当作完整历史重放，也不能当未见留出集。

校验数据集（不会连接 P4、模型或 TAPD）：

```powershell
node dist/index.js eval --dataset docs/accuracy-development-cases.json
```

严格对照结果使用 `EvaluationDataset` 与 `PairedTrial`（`src/evaluationDataset.ts`）格式，数据集为 JSON，结果为 JSONL：

```powershell
node dist/index.js eval --dataset evaluation/frozen.json --result A=evaluation/a.jsonl --result B=evaluation/b.jsonl
```

校验同组不跨开发/留出集、留出时间、冻结版本、测试/预算哈希、配对次数、独立工作区身份和答案检索排除；未产出 candidate_id=null 仍计入 top-1 分母。它校验记录，不创建隔离 P4 client，也不保证调用者填入的工作区身份真实。仅保留 `eval` 与这一套数据格式；旧 JSONL 数据集、加权分和 `eval-paired` 命令已移除。空结果组、重复组名、重复试验会明确报错。

## 验证与后续实测

- 首次实现曾在真实数据库备份上验证历史14条反馈保持不变；按开发阶段要求，当前已移除旧 schema 自动迁移。本轮未修改真实数据库。
- 统一协议后全量323项测试通过，TypeScript构建及页面脚本语法检查通过；`eval` 正确识别14例标签、0例可重放。
- 目录自动发现改造后全量338项测试通过、构建成功；本地新配置自动发现3套测试，11个断言在真实源码上前后均通过。覆盖脚本增删、元数据修改、停用、多文件触发、静态发现不执行脚本以及当前尝试冻结后不受文件删除影响。
- 协议回归覆盖HTTP无候选请求拒绝、历史基线不随新反馈改变、评审维度必填、旧数据集拒绝，以及空/重复试验组拒绝。
- 当前真实数据库只读检查：所需列齐全，14条历史反馈仍在；本轮未重启服务或启动修复队列。
- 三套专项在隔离的当前源码副本中构造对应错误，再恢复原方法：均取得目标断言失败→通过和正常对照通过。此为测试有效性检查，不是历史P4版本重放；真实游戏源码未改动。
- 单元和流程回归包含非空补丁、失败快照、反馈归属、取消、冻结测试防篡改、真实方法执行、正常路径回归、引用合法性、范围补充、评测泄漏和内容索引失效。
- 隔离内存数据库的管理台检查：统计空值、候选哈希/版本、业务验收与待验证项、反馈必须选择具体候选；没有使用生产控制按钮。

独立验证准备当前采用维护好的外部 suites，没有自动生成任意测试并自行定分。首批领域经验来自关联人工反馈，仍待逐题核查当前代码。完整跨文件语言服务、自动恢复历史 P4/资源环境，以及第二套修复候选属于方案中按收益决定的后续实验，当前没有自动启用。

这批改动建立了提高准确率的执行和测量条件，不能把本仓库测试通过宣称为业务准确率已经提高。下一批30–50个新工单应按时间留出，继续记录原样接受、修改后接受、拒绝/重开、覆盖率和人工耗时，再与固定基线比较。
