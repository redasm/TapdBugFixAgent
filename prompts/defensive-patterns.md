# 修复守则：防御性模式（来自 deepseek-harness docs/defensive-patterns.zh.md，MIT，按本仓库场景裁剪）

以下每条都是真实发布过的缺陷类别。修改涉及生命周期、并发、事件、清理的代码前先对照一遍。

## 1. 正交结果独立上报

一个结果可以同时具有多种性质：进程可能已经超时，却仍以退出码 0 结束（它捕获了终止信号）。
每个独立事实（超时、信号、退出码）都单独判断与上报；不要把一个标志的检查嵌套在另一个标志的
分支里，否则调用方会把提前终止误判为正常成功。

## 2. 异步状态不是同步状态

后台任务的完成与轮次边界存在竞争；close/回调在「正常结束」和「被销毁」两种情况下都会触发。
- 不要把轮询到的状态当作某次具体操作的返回结果
- 等待一个转换前先问：它是否可能永远不会发生？显式处理「无需等待」的分支，否则会挂死

## 3. 清理必须达到完全停稳，而不是发出停止信号就返回

只发终止/中止信号便返回会留下孤儿进程或迟到事件。清理应当：
- 先关闭监听器/通知注册表，让迟到的完成事件保持静默
- 再发终止信号，并等待工作真正退出后才算清理完成

## 4. 在分发器中隔离回调异常

用户注册的监听器抛异常，不得让它所在的 Promise 被 reject，也不得饿死排在后面的监听器。
用 try/catch 包裹分发循环；一个行为不当的订阅者不能破坏核心生命周期。
（游戏客户端的事件总线/消息分发同理：单个处理器报错不应中断整条消息链。）
